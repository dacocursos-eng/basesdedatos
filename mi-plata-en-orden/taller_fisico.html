El modelo físico de Mi plata en orden

De las entidades del modelo lógico a las tablas de MySQL.

Apreciados estudiantes:

En este taller van a construir en MySQL una parte del modelo físico de Mi plata en orden: van a escribir el script que crea las tablas, con sus llaves y sus restricciones, a poblarlas con datos del caso y a practicar las sentencias para actualizar, eliminar y consultar. Es el mismo trabajo que van a hacer en la tercera entrega con el modelo de su plataforma de eventos y networking.

Primero preparamos MySQL y revisamos el modelo de partida. Después vienen las tareas, un reto para quienes terminen antes y una estructura sugerida para organizar el script.

Si quieren repasar algún ejemplo, la sesión del modelo físico está disponible aquí: Del modelo lógico al modelo físico.

Antes de empezar

Preparar MySQL

Van a trabajar con MySQL 8.0.16 o una versión posterior, que es la que aplica las restricciones CHECK. Pueden escribir y ejecutar el script en MySQL Workbench o en la consola de MySQL.

Les recomiendo escribir el script en un archivo .sql que compartan en el grupo, y empezarlo con estas líneas, que crean una base de datos nueva para el taller:

DROP DATABASE IF EXISTS mi_plata_taller;
CREATE DATABASE mi_plata_taller;
USE mi_plata_taller;
SET NAMES utf8mb4;

La primera línea elimina la base de datos si ya existe; así pueden corregir el script y volver a ejecutarlo completo desde el principio todas las veces que lo necesiten. La última hace que MySQL guarde bien las tildes y la eñe.

Las tareas

Crear las tablas

Escriban una sentencia CREATE TABLE por cada una de las siete tablas del núcleo. Estas son las tablas y sus relaciones:

PK: llave primaria (subrayada)FK: llave foráneaCírculo: ceroBarra: unoPata de gallo: muchos

Cada tabla se crea después de las tablas a las que hace referencia. Les propongo este orden:

  • ciudad, tipo_cuenta y monedaNo tienen llaves foráneas.
  • personaHace referencia a ciudad.
  • cuenta y categoriaHacen referencia a persona; la cuenta, también a tipo_cuenta y moneda.
  • movimientoHace referencia a cuenta y a categoria.

En cada tabla definan:

Qué definirCómo decidirlo
El tipo de dato de cada columnaSegún los valores que guarda: números enteros, dinero, textos, fechas. En la sesión está el cuadro de tipos de datos.
NULL o NOT NULLCon la cardinalidad mínima del diagrama y con las reglas de negocio de la siguiente diapositiva.
PRIMARY KEYLa columna marcada con PK en el diagrama. Si es un número, usen AUTO_INCREMENT.
FOREIGN KEYUna por cada columna marcada con FK, con su acción ON DELETE y ON UPDATE, y un comentario que explique por qué la eligieron.

La tabla tipo_cuenta de la sesión les sirve de modelo para empezar.

Las tareas

Las reglas de negocio en las tablas

Algunas reglas de negocio de la primera entrega se cumplen con restricciones en las tablas del núcleo. Para cada una, elijan la restricción que corresponde (NOT NULL, UNIQUE, CHECK, DEFAULT o FOREIGN KEY) y nómbrenla con CONSTRAINT.

ReglaTablaQué debe garantizar la tabla
RN_001personaQue dos personas no tengan el mismo correo.
RN_002cuentaQue cada cuenta tenga una persona, y que esa persona exista.
RN_003cuentaQue cada cuenta tenga una moneda, y que esa moneda exista.
RN_005tipo_cuentaQue la clase sea solo activo o pasivo.
RN_006cuentaQue el estado sea solo activa o cerrada, y que una cuenta nueva quede activa.
RN_007cuentaQue el día de corte y el día de pago estén entre 1 y 31, y que el cupo sea mayor que cero. Estos tres datos quedan vacíos en las cuentas que no son tarjetas de crédito.
RN_008movimiento y categoriaQue cada movimiento tenga una categoría que exista, y que la naturaleza de la categoría sea solo ingreso o gasto.
RN_009movimientoQue el valor sea mayor que cero.
RN_014movimientoQue el número de cuotas sea mayor o igual a uno. Queda vacío en los movimientos que no son compras a cuotas.

Las tareas

Poblar las tablas

Escriban las sentencias INSERT para poblar las tablas en el mismo orden en que las crearon. Les propongo usar personas, cuentas y movimientos parecidos a los que contó Catalina, como el arriendo, el mercado, el tinto o la compra de un electrodoméstico a cuotas. Como mínimo:

  • tres ciudades y dos monedas;
  • los siete tipos de cuenta de la regla RN_005, con su clase;
  • dos personas;
  • cinco cuentas, entre ellas una de efectivo y una tarjeta de crédito con su cupo, su día de corte y su día de pago;
  • ocho categorías, entre ellas dos subcategorías y una categoría propia de una persona;
  • doce movimientos de ingreso y de gasto, entre ellos una compra a cuotas.

Después de poblar cada tabla, revisen su contenido con SELECT * FROM y el nombre de la tabla.

Las tareas

Probar las restricciones

Una restricción funciona cuando MySQL rechaza los datos que la incumplen. Escriban al menos cinco sentencias que deberían ser rechazadas, ejecútenlas una por una y copien debajo de cada una, como comentario, la respuesta de MySQL. Por ejemplo:

  • un movimiento con valor cero;
  • una persona con un correo que ya está registrado;
  • una tarjeta de crédito con día de corte 35;
  • una cuenta para una persona que no existe;
  • un tipo de cuenta con una clase distinta de activo o pasivo;
  • eliminar una categoría que tiene movimientos.

Si alguna de estas sentencias es aceptada, revisen la restricción correspondiente en el script de creación.

Las tareas

Actualizar, eliminar y consultar

Escriban una sentencia para cada tarea. Los valores X y Y los eligen ustedes, de acuerdo con los datos que registraron.

UPDATE

  • Cambiar el correo de la persona X.
  • Aumentar el cupo de la tarjeta de crédito X.
  • Cerrar la cuenta X.
  • Corregir la descripción y el valor del movimiento X.

DELETE

  • Eliminar el movimiento X.
  • Eliminar una categoría que no tenga movimientos.
  • Intentar eliminar una persona que tiene cuentas, y explicar en un comentario la respuesta de MySQL según la acción ON DELETE que eligieron.

SELECT

  • Todas las personas registradas.
  • Las cuentas activas de la persona X.
  • Los movimientos de la cuenta X, con su fecha, su descripción y su valor.
  • Las categorías de gasto.
  • Los movimientos con valor mayor que Y.
  • Las subcategorías de la categoría X.
  • Las cuentas que no tienen día de corte.
  • Los movimientos registrados entre dos fechas X y Y.

Antes de cada UPDATE y cada DELETE, consulten con un SELECT y la misma condición cuáles registros van a cambiar.

El reto

Reto: la entidad financiera

Para quienes terminen antes, les propongo completar la relación de la cuenta con la entidad financiera, que en el modelo lógico depende de otras dos tablas:

  • creen las tablas pais, tipo_entidad y entidad_financiera, y puéblenlas;
  • agreguen a la tabla cuenta la columna id_entidad y su llave foránea con ALTER TABLE, sin volver a crear la tabla;
  • asignen con UPDATE la entidad financiera de cada cuenta, y dejen sin entidad la cuenta de efectivo (RN_004);
  • consulten las cuentas que no tienen entidad financiera.

Piensen qué acción ON DELETE conviene para esta llave foránea, teniendo en cuenta que la columna admite valores vacíos.

La revisión

Preguntas para revisar el script

Antes de dar por terminado el script, revísenlo con estas preguntas:

  • ¿El script se ejecuta completo, de principio a fin, sin errores, sobre una base de datos vacía?
  • ¿Cada tabla tiene su llave primaria, y cada relación del modelo lógico, su llave foránea?
  • ¿Las columnas que admiten NULL corresponden con relaciones opcionales o con datos que no siempre se conocen?
  • ¿Cada regla de negocio que se puede verificar en los datos de la fila quedó como restricción?
  • ¿La acción ON DELETE de cada llave foránea tiene sentido para el negocio de Catalina?
  • ¿Los tipos de datos permiten guardar todos los valores del caso, por ejemplo un arriendo de 1.200.000 pesos o una tasa de 28,50 %?
  • ¿Cada UPDATE y cada DELETE tiene una condición que afecta solo los registros que se querían cambiar?
