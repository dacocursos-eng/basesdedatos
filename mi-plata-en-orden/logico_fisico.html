En esta sesión damos el último paso del diseño: transformar ese modelo lógico en el modelo físico, es decir, en las tablas de una base de datos real, y empezar a trabajar con sus datos.

Primero vemos qué es SQL y cómo se organizan sus sentencias. Después transformamos el modelo lógico en tablas, con sus llaves y sus restricciones, y practicamos las sentencias para agregar, actualizar, eliminar y consultar datos. Es lo que van a construir para su proyecto en la tercera entrega.

Los ejemplos están escritos para MySQL 8.0.16 o una versión posterior, y se ejecutaron sobre la base de datos de Mi plata en orden. Las respuestas de MySQL que aparecen en las diapositivas son las que se obtuvieron al ejecutarlos.

El camino

El modelo físico en el camino del diseño

El modelo físico es el último de los modelos del proceso de abstracción. Se obtiene por transformación del modelo lógico y corresponde con el esquema de la base de datos en un sistema gestor de bases de datos (SGBD) concreto, en nuestro caso MySQL.

  • RealidadEl negocio tal como lo explicó Catalina.
  • Modelo conceptualConceptos, características y relaciones.
  • Modelo lógicoEntidades, atributos y llaves, en tercera forma normal.
  • Modelo físicoTablas, columnas, tipos de datos y restricciones en el SGBD.

Desde aquí hablamos de tablas y columnas. Cada tabla se crea con una sentencia del lenguaje SQL, y el conjunto de esas sentencias forma el script de creación de la base de datos: un archivo que se puede guardar, revisar y volver a ejecutar para construir la base de datos completa.

El lenguaje SQL

El lenguaje SQL y sus grupos de sentencias

SQL (Structured Query Language) es el lenguaje estándar para trabajar con bases de datos relacionales. Sus sentencias se organizan en tres grupos, según lo que hacen:

DDL · Definición de datosCrea y modifica la estructura.CREATEALTERDROP
DML · Manipulación de datosAgrega, cambia, elimina y consulta los datos.INSERTUPDATEDELETESELECT
DCL · Control de accesoOtorga y retira permisos.GRANTREVOKE

Con las sentencias de definición de datos se construye y se modifica la estructura: crear una tabla, agregarle una columna o eliminarla. Con las de manipulación de datos se trabaja con la información guardada en esa estructura: agregar registros, actualizarlos, eliminarlos y consultarlos. Las de control de acceso definen qué puede hacer cada usuario de la base de datos.

En esta sesión trabajamos con las dos primeras. Empezamos por CREATE, que construye las tablas a partir del modelo lógico.

Para obtener el modelo físico, cada elemento del modelo lógico se transforma así:

  • Entidades a tablasCada entidad pasa a ser una tabla con el mismo nombre.
  • Atributos a columnasCada atributo pasa a ser una columna con su tipo de dato, y se define si admite valores vacíos (NULL) o no (NOT NULL). La llave primaria se declara con PRIMARY KEY.
  • Relaciones a llaves foráneasCada llave foránea se declara con FOREIGN KEY y la tabla a la que hace referencia.
  • RestriccionesLas reglas de negocio que se pueden verificar en los datos se declaran con NOT NULL, UNIQUE y CHECK.

Vamos a recorrer cada transformación con las tablas de Mi plata en orden.

Las transformaciones

Los tipos de datos

Cada columna tiene un tipo de dato, que define qué valores puede guardar y cuánto espacio ocupa. Estos son los tipos que usamos en Mi plata en orden:

Tipo en MySQLQué guardaEjemplo del caso
INT UNSIGNEDNúmeros enteros sin signo. Con AUTO_INCREMENT, MySQL asigna el siguiente número a cada registro nuevo.id_persona, id_cuenta
TINYINT UNSIGNEDEnteros pequeños, de 0 a 255.dia_corte, numero_cuotas
DECIMAL(14,2)Números exactos con decimales: 14 dígitos en total, 2 de ellos decimales. Es el tipo indicado para el dinero, porque guarda el valor sin redondeos.valor, saldo_inicial, cupo
VARCHAR(n)Textos de longitud variable, hasta n caracteres.nombres, correo, descripcion
CHAR(n)Textos de longitud fija.codigo_moneda (COP), ultimos_cuatro
DATEFechas, en el formato 'AAAA-MM-DD'.fecha_ocurrencia, mes
DATETIMEFecha y hora.fecha_registro del movimiento

Elegir el tipo es parte del diseño. Los últimos cuatro números de una cuenta se guardan como texto, en CHAR(4), porque forman un código que puede empezar por cero y con el que no se hacen operaciones; el valor de un movimiento se guarda en DECIMAL, porque con él se suma y se compara.

Las transformaciones

Entidades a tablas y atributos a columnas

La sentencia CREATE TABLE crea una tabla con sus columnas. Esta es la tabla tipo_cuenta, que en el modelo lógico tiene una llave primaria y dos atributos:

CREATE TABLE tipo_cuenta (
  id_tipo_cuenta INT UNSIGNED NOT NULL AUTO_INCREMENT,
  nombre         VARCHAR(40)  NOT NULL,
  clase          VARCHAR(10)  NOT NULL,
  PRIMARY KEY (id_tipo_cuenta)
);

Cada línea define una columna con su nombre, su tipo de dato y si admite valores vacíos. Al final, PRIMARY KEY indica cuál columna, o cuáles columnas, forman la llave primaria. Una llave primaria nunca admite valores vacíos y no repite valores, así que MySQL garantiza que cada registro se pueda identificar.

Cuando la llave primaria está formada por varias columnas, como en la cuota, se escriben todas dentro del paréntesis: PRIMARY KEY (id_movimiento, numero).

Las transformaciones

NULL o NOT NULL

Para cada columna se decide si es obligatoria (NOT NULL) o si puede quedar vacía (NULL). La decisión sale de la cardinalidad mínima del modelo y de las reglas de negocio. En el modelo lógico, la cuenta se relaciona con cuatro tablas, y solo la relación con la entidad financiera tiene cardinalidad mínima cero:

PK: llave primaria (subrayada)FK: llave foráneaCírculo: ceroBarra: unoPata de gallo: muchos
CREATE TABLE cuenta (
  id_cuenta           INT UNSIGNED     NOT NULL AUTO_INCREMENT,
  id_persona          INT UNSIGNED     NOT NULL,   -- RN_002: toda cuenta es de una persona
  id_tipo_cuenta      INT UNSIGNED     NOT NULL,
  id_entidad          INT UNSIGNED     NULL,       -- RN_004: el efectivo no tiene entidad
  codigo_moneda       CHAR(3)          NOT NULL,   -- RN_003: toda cuenta maneja una moneda
  nombre              VARCHAR(60)      NOT NULL,
  ultimos_cuatro      CHAR(4)          NULL,
  saldo_inicial       DECIMAL(14,2)    NOT NULL DEFAULT 0,
  fecha_saldo_inicial DATE             NOT NULL,
  estado              VARCHAR(10)      NOT NULL DEFAULT 'activa',
  cupo                DECIMAL(14,2)    NULL,       -- RN_007: solo en tarjetas de crédito
  dia_corte           TINYINT UNSIGNED NULL,
  dia_pago            TINYINT UNSIGNED NULL,
  PRIMARY KEY (id_cuenta)
);

Las llaves foráneas de las relaciones con mínimo uno son NOT NULL, y la de la entidad financiera, con mínimo cero, admite NULL. El cupo, el día de corte y el día de pago también admiten valores vacíos, porque solo aplican a las tarjetas de crédito.

La palabra DEFAULT define el valor que toma la columna cuando el registro se agrega sin ese dato: una cuenta nueva queda activa y con saldo inicial cero, salvo que se indique otra cosa. En el porcentaje de alerta del presupuesto, por ejemplo, la regla RN_013 se cumple con DEFAULT 80.

Las llaves foráneas

Las relaciones se transforman en llaves foráneas

La relación entre la persona y la cuenta del modelo lógico se declara en la tabla del lado muchos, la cuenta, con FOREIGN KEY:

CONSTRAINT fk_cuenta_persona FOREIGN KEY (id_persona)
  REFERENCES persona (id_persona)

Con esta declaración, MySQL verifica que cada valor de id_persona en la cuenta exista en la tabla persona. Por eso las tablas se crean en orden: primero las que no tienen llaves foráneas, como ciudad, moneda y tipo_cuenta; después persona; después cuenta, y así sucesivamente. Si se intenta crear la cuenta antes que la persona, MySQL responde que no encuentra la tabla a la que hace referencia.

La palabra CONSTRAINT le da un nombre a la restricción. Es opcional, y nombrarlas con un prefijo, como fk_ para las llaves foráneas, uq_ para UNIQUE y ck_ para CHECK, permite reconocer en los mensajes de error cuál regla se incumplió.

Las llaves foráneas

Llaves compuestas y tablas intermedias

Las tablas intermedias que resolvieron las relaciones de muchos a muchos tienen una llave primaria formada por dos llaves foráneas. Así queda, en el modelo lógico y en el físico, la tabla que une los movimientos con sus etiquetas:

PK: llave primaria (subrayada)FK: llave foráneaCírculo: ceroBarra: unoPata de gallo: muchos
CREATE TABLE movimiento_etiqueta (
  id_movimiento INT UNSIGNED NOT NULL,
  id_etiqueta   INT UNSIGNED NOT NULL,
  PRIMARY KEY (id_movimiento, id_etiqueta),
  CONSTRAINT fk_me_movimiento FOREIGN KEY (id_movimiento)
    REFERENCES movimiento (id_movimiento),
  CONSTRAINT fk_me_etiqueta FOREIGN KEY (id_etiqueta)
    REFERENCES etiqueta (id_etiqueta)
);

La llave primaria compuesta garantiza que una misma etiqueta no se asigne dos veces al mismo movimiento. Las columnas de una llave foránea tienen el mismo tipo de dato que la llave primaria a la que hacen referencia; por eso id_movimiento es INT UNSIGNED en las dos tablas.

Cuando dos columnas de una tabla hacen referencia a la misma tabla, cada una lleva un nombre que explica su significado. En el traslado, id_cuenta_origen e id_cuenta_destino hacen referencia a la cuenta, y cada una representa una de las dos relaciones del modelo:

CONSTRAINT fk_traslado_origen FOREIGN KEY (id_cuenta_origen)
  REFERENCES cuenta (id_cuenta),
CONSTRAINT fk_traslado_destino FOREIGN KEY (id_cuenta_destino)
  REFERENCES cuenta (id_cuenta)

Las llaves foráneas

ON DELETE y ON UPDATE

Cada llave foránea define qué pasa con los registros que la usan cuando se elimina o se actualiza el registro al que hacen referencia. En el movimiento, Julián eligió una acción distinta para cada relación:

PK: llave primaria (subrayada)FK: llave foráneaCírculo: ceroBarra: unoPata de gallo: muchos
CONSTRAINT fk_cuota_movimiento FOREIGN KEY (id_movimiento)
  REFERENCES movimiento (id_movimiento)
  ON DELETE CASCADE
  ON UPDATE CASCADE
OpciónQué haceDónde la usa Julián
RESTRICT o NO ACTIONImpide eliminar o actualizar el registro mientras otros registros lo usen. En MySQL las dos opciones funcionan igual, y es el comportamiento por omisión.Una categoría con movimientos no se puede eliminar; así se protege la información registrada.
CASCADEAplica la misma operación a los registros que lo usan: si se elimina el registro, también se eliminan ellos.Las cuotas de una compra: si se elimina la compra, sus cuotas dejan de tener sentido.
SET NULLDeja vacía la llave foránea de los registros que lo usan. Exige que la columna admita NULL.El tercero de un movimiento: si se elimina el tercero, el movimiento se conserva sin él.
SET DEFAULTAsigna el valor por omisión de la columna. Hace parte del estándar, y el motor InnoDB de MySQL no la admite.No se usa.

La elección depende de la relación: RESTRICT protege los datos, CASCADE sirve para los registros que dependen por completo de otro, como los conceptos débiles, y SET NULL sirve para las relaciones opcionales.

Las restricciones

Las reglas de negocio se convierten en restricciones

Las restricciones limitan los valores que se pueden guardar en una columna. Muchas de las reglas de negocio de la primera entrega llegan al modelo físico así:

Regla de negocioRestricción en el modelo físico
RN_001 El correo de cada persona es único.CONSTRAINT uq_persona_correo UNIQUE (correo)
RN_009 El valor de un movimiento es mayor que cero.CONSTRAINT ck_movimiento_valor CHECK (valor > 0)
RN_007 El día de corte está entre 1 y 31.CONSTRAINT ck_cuenta_dia_corte CHECK (dia_corte BETWEEN 1 AND 31)
RN_006 El estado de una cuenta es activa o cerrada.CONSTRAINT ck_cuenta_estado CHECK (estado IN ('activa', 'cerrada'))
RN_012 Cada persona tiene como máximo un presupuesto por mes.CONSTRAINT uq_presupuesto_persona_mes UNIQUE (id_persona, mes)
RN_013 El porcentaje de alerta está entre 1 y 100, y es 80 por omisión.DEFAULT 80 y CHECK (porcentaje_alerta BETWEEN 1 AND 100)
RN_019 Una tasa de cambio por moneda y fecha.PRIMARY KEY (codigo_moneda, fecha)

NOT NULL obliga a registrar el dato; UNIQUE impide que un valor, o una combinación de valores, se repita; CHECK verifica una condición sobre los valores de la fila. MySQL aplica las restricciones CHECK desde la versión 8.0.16.

Algunas reglas comparan datos de varias tablas, como la RN_011, que pide que las dos cuentas de un traslado sean de la misma persona. Esas reglas se verifican en la aplicación o con disparadores (triggers), un tema que va más allá de esta sesión.

Las restricciones

Modificar una tabla con ALTER TABLE

DDL · Definición de datosCrea y modifica la estructura.CREATEALTERDROP
DML · Manipulación de datosAgrega, cambia, elimina y consulta los datos.INSERTUPDATEDELETESELECT
DCL · Control de accesoOtorga y retira permisos.GRANTREVOKE

Las restricciones se pueden declarar al crear la tabla o agregar después con ALTER TABLE, que modifica la estructura de una tabla que ya existe:

-- Agregar una restricción UNIQUE
ALTER TABLE persona ADD CONSTRAINT uq_persona_correo UNIQUE (correo);

-- Volver obligatoria una columna
ALTER TABLE persona MODIFY celular VARCHAR(15) NOT NULL;

-- Agregar una restricción CHECK
ALTER TABLE movimiento ADD CONSTRAINT ck_movimiento_valor CHECK (valor > 0);

-- Agregar una columna con su llave foránea
ALTER TABLE cuenta ADD COLUMN id_entidad INT UNSIGNED NULL;
ALTER TABLE cuenta ADD CONSTRAINT fk_cuenta_entidad FOREIGN KEY (id_entidad)
  REFERENCES entidad_financiera (id_entidad) ON DELETE SET NULL;

Si la tabla ya tiene datos que incumplen la restricción, por ejemplo personas sin celular, MySQL no la agrega hasta que esos datos se corrijan. Para eliminar una tabla completa, con su estructura y sus datos, se usa DROP TABLE; para eliminar la base de datos completa, DROP DATABASE. Por eso los scripts de creación suelen empezar con DROP DATABASE IF EXISTS, que permite volver a ejecutarlos desde cero.

La manipulación de datos

Agregar registros con INSERT

DDL · Definición de datosCrea y modifica la estructura.CREATEALTERDROP
DML · Manipulación de datosAgrega, cambia, elimina y consulta los datos.INSERTUPDATEDELETESELECT
DCL · Control de accesoOtorga y retira permisos.GRANTREVOKE

INSERT INTO agrega registros a una tabla. Se puede escribir de dos formas:

-- Sin nombrar las columnas: los valores van en el orden en que se definieron en la tabla
INSERT INTO moneda VALUES ('COP', 'Peso colombiano');

-- Nombrando las columnas: los valores van en el orden de la sentencia
INSERT INTO persona (id_ciudad, nombres, apellidos, correo, celular, fecha_registro)
VALUES (1, 'Sofía', 'Ramírez Gómez', 'sofia.r@correo.com', '3001234567', '2026-08-01');

La segunda forma es la recomendada: el script se entiende mejor, y las columnas que no se nombran toman su valor por omisión o quedan vacías. Por eso no se escribe id_persona: MySQL lo asigna con AUTO_INCREMENT.

Los textos y las fechas van entre comillas simples, y las fechas en el formato 'AAAA-MM-DD'. Los números se escriben sin separador de miles y con punto decimal: 1200000 o 28.50. Para dejar un dato vacío se escribe NULL, sin comillas. Una misma sentencia puede agregar varios registros, separando cada grupo de valores con una coma.

La manipulación de datos

INSERT y las llaves foráneas

Cuando una tabla tiene llaves foráneas obligatorias, el registro al que hacen referencia debe existir antes. Por eso las tablas se pueblan en el mismo orden en que se crearon: primero la persona y después sus cuentas.

Si se intenta registrar una cuenta para una persona que no existe:

INSERT INTO cuenta (id_persona, id_tipo_cuenta, codigo_moneda, nombre, fecha_saldo_inicial)
VALUES (9, 1, 'COP', 'Cuenta nueva', '2026-11-01');
Respuesta de MySQL: ERROR 1452 (23000): Cannot add or update a child row: a foreign key constraint fails (`mi_plata_en_orden`.`cuenta`, CONSTRAINT `fk_cuenta_persona` FOREIGN KEY (`id_persona`) REFERENCES `persona` (`id_persona`) ON DELETE RESTRICT ON UPDATE CASCADE)

Las restricciones también se verifican en cada INSERT. Un movimiento con valor cero o una persona con un correo que ya existe son rechazados:

INSERT INTO movimiento (id_cuenta, id_categoria, fecha_ocurrencia, valor, descripcion)
VALUES (1, 5, '2026-11-05', 0, 'Mercado');
Respuesta de MySQL: ERROR 3819 (HY000): Check constraint 'ck_movimiento_valor' is violated.

El nombre de la restricción en el mensaje indica cuál regla se incumplió; esa es la utilidad de nombrarlas.

La manipulación de datos

Actualizar registros con UPDATE

DDL · Definición de datosCrea y modifica la estructura.CREATEALTERDROP
DML · Manipulación de datosAgrega, cambia, elimina y consulta los datos.INSERTUPDATEDELETESELECT
DCL · Control de accesoOtorga y retira permisos.GRANTREVOKE

UPDATE cambia los valores de una o varias columnas en los registros que cumplen la condición del WHERE:

UPDATE nombre_tabla
SET columna1 = valor1, columna2 = valor2
WHERE condicion;
-- Sofía cambia su correo
UPDATE persona
SET correo = 'sofia.ramirez@correo.com'
WHERE id_persona = 1;

-- Sofía paga la segunda cuota de la nevera
UPDATE cuota
SET estado = 'pagada'
WHERE id_movimiento = 9 AND numero = 2;

La condición del WHERE define cuáles registros se modifican, así que conviene escribirla con cuidado y, cuando sea posible, usar la llave primaria. Sin WHERE, la sentencia se aplica a todos los registros de la tabla. En la tabla persona, un UPDATE persona SET correo = 'nuevo@correo.com'; sin condición intentaría dejar a todas las personas con el mismo correo, y la restricción UNIQUE del correo lo impide:

Respuesta de MySQL: ERROR 1062 (23000): Duplicate entry 'nuevo@correo.com' for key 'persona.uq_persona_correo'

DELETE FROM elimina los registros que cumplen la condición del WHERE. Como en el UPDATE, sin condición se eliminan todos los registros de la tabla.

DELETE FROM nombre_tabla
WHERE condicion;

Al eliminar, MySQL aplica la acción que definimos en cada llave foránea:

-- RESTRICT: la categoría Mercado tiene movimientos
DELETE FROM categoria WHERE id_categoria = 5;
Respuesta de MySQL: ERROR 1451 (23000): Cannot delete or update a parent row: a foreign key constraint fails (`mi_plata_en_orden`.`movimiento`, CONSTRAINT `fk_movimiento_categoria` ...)
-- CASCADE: al eliminar la compra de la nevera se eliminan también sus tres cuotas
DELETE FROM movimiento WHERE id_movimiento = 9;

-- SET NULL: al eliminar el supermercado, sus movimientos se conservan sin tercero
DELETE FROM tercero WHERE id_tercero = 1;

Antes de eliminar, vale la pena consultar con un SELECT y la misma condición cuáles registros se van a eliminar.
